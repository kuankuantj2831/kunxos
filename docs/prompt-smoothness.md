# 提示词：KunxOS 流畅度专项优化

> 使用方法：把下面的「提示词正文」整段复制给任意代码 AI，让它直接对仓库动手。
> 项目根目录：KunxOS（ARM64 从零操作系统，Rust + 少量汇编，`no_std`，无外部依赖）。

---

## 提示词正文

你是 KunxOS 项目的系统工程师。KunxOS 是一个从零编写的 ARM64 操作系统，内核（`kunxcore/`）用 Rust 编写，`no_std`、无外部 crate，目标平台是 QEMU `virt`（Cortex-A72），图形走 ramfb 帧缓冲（540×960×32bpp）。图形、合成器、动画引擎、UI 框架、shell 都在内核态（EL1）。构建用顶层 `Makefile`：`make kernel` 编译内核，`make run-gui` 用 QEMU 带图形运行。

你的任务：**在不破坏现有功能的前提下，全面提升系统的"流畅度"**——即降低动画帧间隔抖动、降低每帧合成/呈现开销、加快应用启动、降低输入到画面的延迟。以下按优先级给出诊断与改动指引，请逐项实现。

### 工作方式

1. 先通读这些文件，建立完整认识（按顺序）：
   `kunxcore/src/main.rs`（初始化与定时器注册）、`kunxcore/src/timer.rs`、`kunxcore/src/anim.rs`（帧推进）、`kunxcore/src/compositor.rs`（合成与呈现）、`kunxcore/src/vm.rs`（页表/映射）、`kunxcore/src/process.rs`（fork）、`kunxcore/src/elf.rs`（ELF 加载）、`kunxcore/src/sched_cfs.rs`（调度器）、`kunxcore/src/allocator.rs` + `kunxcore/src/heap.rs`（内存分配）。
2. 每完成一项改动，运行 `make kernel` 确认编译通过；全部完成后运行 `make run-gui` 确认系统仍能启动、OOBE/launcher/动画自检输出正常。
3. 改动必须保持：`no_std`、无新增外部 crate、现有系统调用 ABI 不变、ELF 与磁盘镜像格式不变（`tools/` 与 `Makefile` 不动）、不改变 `#![allow(static_mut_refs)]` 下的静态可变全局风格。

### 第 0 步（必须最先做）：加帧间隔度量

在 `anim.rs` 的 `frame_tick()` 里加一个帧间隔统计器：记录每次推进的真实间隔（µs），滚动维护 min / max / avg / p95，每 60 帧向串口打印一次（`uart` 宏）。这是后面所有优化的验收工具，先有度量再优化。

### 第 1 步（P0，帧管线）：消除每帧整屏拷贝

现状：`compositor::present()` 每帧把整个 canvas（540×960×4 ≈ 2MB）`copy_nonoverlapping` 到 back 再翻转——这是动画期间最大的固定开销。

- 方案 A（最小改动）：`composite()` 已经按脏区域重合成，但结束后把 `dirty_count` 清零了，`present()` 拿不到增量。请保留"本帧实际重合成过的区域"（在 composite 中累积），让 `present()` 只增量拷贝脏区域到 back。
- 方案 B（更优，优先评估）：让 `composite()` 直接合成到 back 缓冲（canvas 与 back 合一），`present()` 只做 `gpu_simple::present(back)` + 翻转，完全去掉 canvas→back 拷贝。注意保持双缓冲语义与窗口/脏区域逻辑不变。
- 无论哪个方案，确保窗口移动时新旧位置都被正确标记为脏（检查 `add_dirty` 的矩形合并逻辑是否已覆盖）。

### 第 2 步（P0，帧管线）：合成快速路径

现状：`composite()` 对每个像素都做最近邻采样 + `blend_pixel`，即使窗口不透明（alpha=255）也逐像素混合，且 scale≠256 时每像素做整数除法。

- alpha == 255（不透明）：直接按行 `copy_nonoverlapping`，不要走逐像素混合；
- scale == 256（1:1）：行级整行拷贝；scale ≠ 256：把最近邻采样改成按行预计算映射（每行算一次源偏移，避免每像素除法）；
- alpha == 0 的窗口直接跳过；
- 目标是让"单窗口 1:1 不透明动画"的合成成本降到近似 memcpy 级别（几百 µs 以内）。

### 第 3 步（P0，帧节奏）：动画帧推进与调度解耦

现状：`anim::frame_tick` 和 `sched_cfs::tick` 注册在同一个 10ms 定时器 IRQ 上（`main.rs` 第 480-484 行），动画帧间隔会被调度器运行时间抖动污染，且被限制在 100Hz。

- 评估把动画推进改为独立、稳定节奏：新增一个专用定时器通道（或复用现有 timer 机制）以固定间隔（如 8ms/10ms）驱动 `frame_tick`，与调度 tick 分离；
- 若实现复杂度过高，至少保证 `frame_tick` 永远在调度 tick **之前**执行（现状已满足），并让第 0 步的统计器证明 p95 达标；
- 输入事件到达时（`input_stack.rs` / `input.rs` 处理路径），若当前无活动动画但有待呈现的 UI 更新，应尽快触发一次合成呈现，而不是等到下一个 tick（低延迟输入路径）。

### 第 4 步（P1，应用启动）：fork 提速

现状：`process.rs` 的 fork 是**完整复制父进程地址空间**（每条用户映射分配新物理页并逐字节拷贝），launcher 拉起应用的开销正比于应用内存。

- 第一层（简单、零风险、立即做）：**共享只读代码段**。`elf.rs` 加载 PT_LOAD 段时，`PF_X`（可执行）段当前每进程拷贝一份物理页——改为跨进程共享同一物理页（页表里本来就是只读映射 `AP_USER_RO`，直接共享即可，不需要 COW 机制）。数据段仍按现状拷贝。
- 第二层（进阶，评估后做）：**写时复制（COW）**。把 fork 的数据页映射为只读并在缺页异常时复制。先检查 `interrupt.rs` 是否已有 data abort（EL1 同步异常）处理入口；若没有，COW 需要新增缺页处理路径，工程量大，请评估后决定是否本期完成，未完成则明确写入"遗留项"。

### 第 5 步（P1，应用启动）：ELF 加载提速

现状：`elf.rs` 的 `load()` 逐页 `copy_nonoverlapping` 拷贝段数据。

- 段内连续区域改为整块 memcpy（减少调用次数与页粒度开销）；
- 结合第 4 步的代码段共享，加载时对代码段直接引用源物理页（从 ramdisk/内核缓冲区映射或登记共享），避免拷贝；
- 顺带检查 `MAX_USER_PAGES = 512`（`vm.rs`）是否成为大应用的内存瓶颈。

### 第 6 步（P2，系统级）：前台进程调度优待

现状：`sched_cfs.rs` 已有 `PriorityClass`，但 GUI 前台进程没有显式优待。

- 给 launcher / 前台应用（最近与输入交互的进程）提升调度优先级或权重，降低动画期间被后台进程抢占的概率；
- 保持 CFS 语义不变，只调整权重映射。

### 第 7 步（P2，系统级）：分配器检查

- 确认动画期间合成路径**零堆分配**（`composite` / `present` / `anim::frame_tick` 不应有每帧 malloc/free，若有请改为复用缓冲区）；
- 若窗口表面在动画期间反复分配/释放，改为对象池复用。

### 验收标准（全部满足才算完成）

1. `make kernel` 与 `make run-gui` 均正常，OOBE、launcher、计算器/设置等应用可交互；
2. 第 0 步的帧间隔统计：优化后 **p95 < 12ms 且无 > 20ms 尖峰**，并附优化前后对比（从串口日志提取）；
3. 应用启动（launcher 拉起 app 到出现首帧）时间较优化前下降，给出前后数据；
4. `anim::self_test` 的曲线数值输出不变（动画规范未改动）；
5. 内核镜像大小不显著膨胀（< 20%）。

### 汇报格式

完成后请输出：① 改动文件清单（含每个文件改了什么）；② 第 0 步统计器优化前后对比数据；③ 应用启动时间前后对比；④ 未完成/遗留项（如 COW 数据段）；⑤ 自检项（编译、运行、动画自检）的通过情况。

## 给项目作者的使用说明

- 该提示词假定接收方 AI 能直接读写仓库并运行 `make`；若你的 AI 没有终端权限，删掉"工作方式"中关于运行 make 的句子，改为让它只改代码并自检语法。
- 第 1 步方案 B（canvas 与 back 合一）若实现遇到困难，退回方案 A（脏区域增量拷贝），两者都满足验收标准 2。
- 第 4 步第二层（COW）是本期最大的不确定项，若接收方 AI 反馈缺页处理缺失导致无法完成，接受"只做代码段共享"的结果并在遗留项中记录。
