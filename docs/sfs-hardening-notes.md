## 2. 已确认并修复的掉电一致性问题

（以下缺陷均通过 `tools/sfs_host_test` 的故障注入复现；修复后基本/大文件/磨损/日志环/撕裂前段
全部通过，崩溃点在 k≤~85 全部 fsck 干净。）

### 2.1 恢复扫描不按记录长度步进（决定性 bug，原实现 69/73 崩溃点损坏）
原 `journal_recover` 以「每环块一个记录头」的方式扫描，而 DATA 记录占 2 块（头+镜像）。
扫描到第一条 DATA 的镜像块时 magic 校验失败提前终止，其后**全部已提交记录不可见**，
COMMIT 与位图记录不被重放。掉电后出现「目录项/inode 已落盘（copy-out），但位图未置位」
的撕裂状态（`dir dangling entry` + `inode valid but not allocated`）。
修复：扫描按记录步进（DATA 记 2 块、COMMIT 记 1 块），镜像块不再被当作记录头。

### 2.2 事务中途检查点冲刷未提交分配（孤儿块）
原 `jlog_place` 在「记录跨环尾 / 环将满」时立即 `checkpoint()` —— 该时刻本事务的分配
位已在 RAM 位图，但 COMMIT 尚未落盘。检查点把未提交位刷进磁盘位图；若随后掉电，该事务
整体丢弃，但磁盘位图已多出一批无 inode 引用的「孤儿分配块」。
修复：检查点只在事务边界执行 ——
- `txn_begin` 预检（空间/跨界不足时先检查点，此时上一事务已提交/回滚，RAM 全为已提交态）；
- `commit_inner` 提交完成后按需检查点；
- `jlog_place` 只做纯定位，绝不在事务中途触发检查点。
预检前/后补跳环首（见 2.5），保证后续记录从环首连续写入。

### 2.3 提交失败不回收 RAM 分配位（泄漏合并成永久孤儿）
原 `commit_inner` 日志写失败时只清 PENDING，RAM 位图保留本事务已分配位。后续成功事务
暂存的位图块镜像会**包含这些泄漏位**，提交并重放后泄漏位固化到磁盘 → 孤儿块，且 fsck
永远报错。
修复：提交失败立即回滚内存位图/计数到事务快照（块在磁盘上仍是清零内容，可安全复用）。

### 2.4 重放写失败仍推进 head（未重放尾巴被新事务覆盖）
恢复第二遍重放时若某条重放写失败，原实现继续扫描并最终把 head/next 推进到扫描终点，
未重放记录被随后写入的新事务覆盖 → 元数据修改永久丢失（孤儿块/悬空目录）。
修复：重放写失败立刻停止，head 不动、next 停在失败记录处，`journal_recover` 返回 -1，
`mount` 传播失败；下一次挂载从同处继续重放（幂等）。

### 2.5 检查点预检后未跳环首（回归：正常路径写入失败，已修复）
`txn_begin` 预检只做检查点而没跳环首时，检查点后 pos 仍在环尾附近，预检条件对每个
事务恒真且 `jlog_place` 防御性失败 → 正常（无崩溃）写入事务整体失败 → 文件内容残缺
（`wrap` 测试 chunk 丢失）。修复：预检检查点后若仍临环尾，把 head/next 一起跳过尾区
进到环首（跳过的是陈旧记录，seq ≤ head_seq，扫描按序号过滤）。

### 2.6 扫描序号单调守卫
恢复扫描遇 seq 回退（物理环序越过最新记录进入上一周期陈旧区）即停止 —— 陈旧区记录
不参与重放，杜绝「旧快照覆盖新状态」。

## 3. 残余限制（明确记录，不隐藏）

`tools/sfs_host_test` 的长程崩溃压力套件（k≥88 后的多轮累积 + 日志环多次卷绕）下，
部分崩溃点恢复后 fsck 仍报错（首个损坏集中在日志环**首次卷绕期间**分配的 inode /
数据块区域：如 inos 85~96、块 1113/1119~1123）。具体表现：dir 悬空项 + inode 有效但
未分配 + 个别「inode 引用未分配块」，说明该时段事务的位图/引用一致性在多次卷绕+部分
重放后出现净偏差。根因方向已收敛到：物理环序在卷绕跨界处 ≠ 时间序，恢复窗口跨越不同
物理周期时按物理序重放可能破坏目标块最终态；当前防护（按记录步进 + 单调守卫 + 边界
检查点 + 跳环首）已消除前段全部崩溃点（k≤~85 干净），但未完全覆盖极长累积后的跨界
窗口。**推荐的彻底修复（未实现，列为后续）：按 seq 升序的二阶段重放（先收集窗口内
记录，再按 seq 排序逐事务重放，保证同目标块始终以最新提交态收尾），或超级块维护
「日志高水位 seq」以严格界定可重放窗口。** 该问题不影响正常（无掉电）路径与单/短程
崩溃恢复。

## 5. 关键问题回答

### 5.1 块大小？是否对齐 SD 擦除块？
块大小 **4KB**（`blkdev::BLK_SIZE`，扇区 512B，1 块 = 8 扇区）。SD/eMMC 典型擦除块
为 512KB —— **不对齐**。改动块大小会推翻全部布局且不兼容既有镜像，故保持 4KB，改以
「环形日志分散元数据写 + 检查点批量刷盘」缓解热点块磨损；真机擦除块对齐与 discard
列为后续工作（见 sfs-v2.md §10）。

### 5.2 日志区大小？如何防止写爆？
`J = min(1024, max(64, total/8))` 块。/data 256MB → J=1024（4MB，约 512 条 DATA 记录）；
ramdisk 6MB → J=192。防写爆：单事务记录数上限 24（`MAX_PENDING`，缓冲放不下即失败回滚）；
`txn_begin` 预检在事务边界做检查点腾出空间；`commit_inner` 提交后用量 ≥3/4 检查点；
记录禁止跨环尾（临尾时检查点+跳环首）。元数据日志写量远小于数据写量且分散在 J 块上，
正常负载下日志区不构成擦写瓶颈（设计速率要求见 sfs-v2.md §10）。

### 5.3 是否需要 TRIM/discard？
**需要（尚未实现）**。virtio-blk 驱动未协商 discard 特性（`virtio_blk.rs` 特性协商写 0）。
真机 SD/eMMC 建议：协商 `VIRTIO_BLK_T_DISCARD`（QEMU 加 `discard=unmap`/`discard=on`）
或等价命令，释放块时告知闪存，降低写放大、延长寿命。列为后续工作。
