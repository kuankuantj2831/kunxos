# 优化轮 044：launcher 交互 t2f（点按→上屏）首基线——avg ~15ms/p95 ~31ms，延迟已不在 syscall 层

- 日期：2026-10-20
- 轮次性质：自动化第 43 轮
- 类型：交互延迟审计（r43 候选池回补）

## 基建扩展

`tools/boot_trace.py`：桌面就绪后按 APPS_DB 坐标点应用图标（clock/
calculator/settings），配合内核 perf.rs 既有 t2f 按帧记录（触控→上屏，
仅输入跟随帧计入）采集交互延迟；行过滤纳入 t2f。

## 首基线（boot_trace 全程到桌面 + 点按，0 PANIC，桌面 21 应用）

| 指标 | 值 | 解读 |
| --- | --- | --- |
| t2f avg | **14.7-16.0 ms** | ≈ 60Hz 帧节拍量级——输入跟随帧落在下一个
呈现节拍 |
| t2f p95 / max | ~31 / ~32 ms | 慢跟随（应用打开重帧） |

## 结论

- **交互延迟已不在内核/syscall 层**（时钟 2.8µs、open 8.7µs、输入注入
  µs 级）：t2f 主导项是应用侧帧节拍（launcher 按需呈现 + MOTION 预算
  节拍）。min 367µs 证明管线本身极快，avg 15ms 是「等下一拍」的节拍
  而非处理耗时。
- 若要压 avg：方向在 launcher 呈现策略（输入事件唤醒即时呈现 vs 节拍
  合批）——产品权衡项（省电 vs 延迟），非缺陷。真机（非 TCG）上预计
  min 亚毫秒不变、avg 由帧时钟决定。
- 附注：calculator/settings 未在 25s 内出就绪标记（clock 就绪 ✓）——
  点击命中或启动时长问题，boot_trace 单次观测不深究，留观。
