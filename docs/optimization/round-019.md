# 优化轮 019：转场真瓶颈定位与根治——玻璃导航预渲染出动画窗口，转场 4→12 帧（~22→64fps，3x）

- 日期：2026-10-18
- 轮次性质：自动化第 18 轮（轮号 018 被并发会话用户直指令轮占用——
  其 launcher 返回转场预烘焙与本轮 OOBE 步间转场预渲染为同思路分战场）
- 类型：动画性能（round-016/017 头号遗留的 phase 分解）

## 本轮目标

转场循环 phase 分解：混合已被 round-016 A/B 证明不是帧数瓶颈，找 ~45ms/帧
的真去处。

## 方法与发现

给 `transition_pages` 加逐相位计时（混合/导航/尾拷/呈现/输入泵，mono_us
×6/帧 扰动 <0.6%），boot_trace 全程采集 12 次转场：

| 相位 | 修复前 µs/帧（均值） | 解读 |
| --- | --- | --- |
| **导航区** | **25,000-33,000（~70%）** | ★ 真凶 |
| 混合 | 8,200-10,600 | 次要 |
| 呈现 | 1,400-3,100 | 小 |
| 尾拷 | 500-1,700 | 小（同数据量行拷仅 ~1ms，佐证恢复分支本身不慢） |
| 泵 | 56-94 | 忽略 |

深挖导航相位：帧 0 的 `draw_nav_anim`（毛玻璃降采样+盒式模糊全量绘制
~120ms）在 160ms 动画窗口内独吞帧 0（~130ms）——**交叉淡化的缓动曲线
实际只剩 t≈0.7 后的 2-3 帧可见，这就是转场顿感的本质**。均值 30ms =
120ms 摊到 4 帧。round-016 的「隔行零增益」之谜同步解开：省 4ms 混合
改变不了 4 帧粒度下的帧数，但帧 0 巨鲸一直在。

## 修复（apps/oobe/src/main.rs）

玻璃+按钮与动画进度 e 无关（仅进度点依赖 e 且本就逐帧重画）——把
`draw_nav_anim(to, 0.0)` + 快照**预渲染到 t0 之前**（setup 阶段，与
render() 同段），循环内删除帧 0 全量绘制分支，只留快照恢复+进度点。
